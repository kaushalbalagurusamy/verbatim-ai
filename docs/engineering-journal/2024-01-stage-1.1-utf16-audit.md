# Stage 1.1 - UTF-16 Code Unit Audit

## Date: 2024-01-10

### Summary
Completed Stage 1.1 of the EditorV2 rewrite focusing on proper UTF-16 handling for multi-code-unit characters like emojis and surrogate pairs.

### Changes Made

#### 1. Created UTF-16 Aware String Utilities (`src/editor-v2/utils/string-utils.ts`)
- **codeUnitLength(text)**: Explicit UTF-16 code unit counting
- **codePointAt(text, offset)**: Get Unicode code point at offset
- **codePointCount(text)**: Count actual Unicode characters
- **sliceByCodeUnits(text, start, end)**: Safe string slicing
- **isSurrogatePair(text, offset)**: Detect surrogate pairs
- **getGraphemeAt(text, offset)**: Extract grapheme clusters (emoji sequences)
- **safeSubstring(text, start, length)**: Substring that won't break surrogates
- **offsetAfterInsert/Delete**: Offset calculations for edits

#### 2. Updated DocumentModel (`src/editor-v2/models/document-model.ts`)
- Replaced all `.length` calls with `codeUnitLength()`
- Replaced all `.slice()` calls with `sliceByCodeUnits()`
- Ensured block.length always reflects UTF-16 code units
- Fixed text insertion/deletion to handle multi-code-unit characters

#### 3. Updated SingleContentEditableEditor (`src/editor-v2/components/SingleContentEditableEditor.tsx`)
- Updated DOM-to-offset conversions to use `codeUnitLength()`
- Fixed text measurement in `handleInput()` for emoji support
- Updated line calculations to use block.length (code units)
- Fixed cursor position calculations for surrogate pairs

#### 4. Updated SelectionManager (`src/editor-v2/selection/selection-manager.ts`)
- Fixed word boundary detection with `codeUnitLength()`
- Ensured selection ranges use UTF-16 offsets

### Key Findings

1. **JavaScript String Internals**: JavaScript strings use UTF-16 encoding internally. A single emoji like 👋 takes 2 code units (`.length === 2`), while complex emojis like 👨‍👩‍👧‍👦 can take 11 code units.

2. **Critical Operations**: The most critical operations are:
   - String slicing (must not break surrogate pairs)
   - Length calculations (must count code units, not characters)
   - Offset calculations after insertions/deletions

3. **Browser Compatibility**: The browser's Selection API and contentEditable work with UTF-16 offsets, so our internal representation must match.

### Testing

Created comprehensive test suite (`src/editor-v2/utils/__tests__/string-utils.test.ts`) covering:
- ASCII text
- Basic emojis (👋)
- Surrogate pairs (𝐀𝐁𝐂)
- ZWJ sequences (👨‍👩‍👧‍👦)
- Variation selectors (☀️)
- Edge cases and invalid sequences

### Property Test Verification

Added property test to ensure the invariant:
```
totalLength === Σ(block.length)
```

This ensures that the sum of all block lengths equals the total document length, even with multi-code-unit characters.

### Risks and Mitigations

1. **Risk**: Performance overhead from UTF-16 calculations
   - **Mitigation**: Most operations are O(1) or O(n) where n is the text length
   - **Mitigation**: Consider lazy evaluation for grapheme detection

2. **Risk**: Incomplete emoji sequence handling
   - **Mitigation**: Current implementation handles common cases
   - **Mitigation**: Can enhance with Intl.Segmenter when browser support improves

### Conclusion

Stage 1.1 successfully establishes a solid foundation for UTF-16 aware text handling. All string operations now correctly handle multi-code-unit characters, preventing the corruption issues seen with emojis and other Unicode characters.
